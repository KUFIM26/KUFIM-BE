# KUFIM 벤치마킹 · 인터뷰 계획

> 1주차 활동("타 서비스 벤치마킹 분석 및 프로젝트 요구사항 정리")의 실행 도구.
> **본 문서는 조사 결과가 아니라 조사 설계다.** 실제 데이터는 직접 사용·인터뷰해서 채운다.

| 항목 | 내용 |
|---|---|
| 문서 버전 | v0.1 |
| 작성일 | 2026-08-31 |
| 상태 | 조사 전 — 표의 셀은 비어 있음 |

---

## 0. 이 문서를 쓰는 이유

계획서 1주차에 "테이블링·캐치테이블 등 국내 웨이팅 서비스와 타 대학 축제 웹사이트를 분석"이 명시되어 있다.
그런데 **분석 축을 먼저 정하지 않으면 앱을 몇 개 켜보고 인상만 남는다.**
여기서 비교 항목과 질문지를 먼저 확정해 두고, 실제 조사에서는 칸을 채우기만 한다.

조사 결과는 다음 두 곳에 직접 반영된다.
- 요구사항 명세서의 미결정 항목(특히 **TBD-01·02 인증/전화번호**, **TBD-04 예상 대기시간 산출식**)
- 3주차 UI/UX 설계의 화면 흐름

## 1. 웨이팅 서비스 벤치마킹

### 1.1 대상

| # | 서비스 | 조사 방법 |
|---|---|---|
| 1 | 테이블링 | 실제 매장에서 원격 웨이팅 등록 후 입장까지 전 과정 이용 |
| 2 | 캐치테이블 | 동일 |
| 3 | 나이스웨이팅 등 매장 태블릿형 | 현장 등록 흐름 관찰 |
| 4 | 타 대학 축제 웹/앱 (2~3개) | 공개된 서비스 접속 |

> **반드시 직접 이용한다.** 스크린샷 검색만으로는 아래 항목 대부분을 채울 수 없다.
> 특히 "호출 알림이 실제로 어떻게 도착하는가"는 우리 프로젝트의 최대 미결정 사항(TBD-03)과 직결된다.

### 1.2 비교 항목

| 축 | 확인할 것 | KUFIM 결정에 미치는 영향 |
|---|---|---|
| **진입 방식** | QR / 앱 / 링크 중 무엇인가. 앱 설치를 강제하는가 | 우리는 앱 미설치 웹 전제 (NFR-C-002) |
| **본인 식별** | 전화번호를 받는가. 회원가입을 요구하는가. 비회원 경로가 있는가 | **TBD-01 / TBD-02** |
| **입력 항목 수** | 등록 완료까지 몇 번 조작하는가 | NFR-U-001 (3회 이하 목표) |
| **대기 정보 표시** | 팀 수만 보여주나, 예상 시간도 주나. 어떤 단위로 갱신되나 | F-WAI-05 화면 설계 |
| **예상 시간 산출** | 값이 어떻게 변하는가. 튀는가, 완만한가. "약 N분"인가 범위인가 | **TBD-04** |
| **호출 알림** | SMS / 푸시 / 화면 표시 중 무엇인가. 몇 분 전에 오는가 | **TBD-03** |
| **노쇼 처리** | 유예 시간이 얼마인가. 자동으로 취소되는가, 직원이 처리하는가 | F-WAI-15 (우리는 자동 전이 안 함) |
| **취소 흐름** | 몇 번 만에 취소되는가. 취소 후 재등록이 되는가 | F-WAI-11 |
| **이탈 후 복귀** | 브라우저를 닫았다 켜면 대기표를 다시 찾을 수 있는가. 어떻게 | F-WAI-12 (익명 토큰 방식 검증) |
| **오프라인·오류** | 네트워크가 끊기면 화면이 어떻게 되는가 | COM-007 |
| **운영자 화면** | (관찰 가능하면) 호출 버튼이 몇 개인가, 오조작 방지가 있는가 | A-03 설계 |

### 1.3 기록 양식

각 서비스마다 아래를 채운다.

```
서비스명:
조사 일시:
조사 방법: (직접 이용 / 관찰 / 자료)

[진입]        
[본인 식별]   
[입력 항목]   
[대기 표시]   
[예상 시간]   
[호출 알림]   
[노쇼]        
[취소]        
[복귀]        
[오류 처리]   

좋았던 점 (우리가 가져올 것):
불편했던 점 (우리가 피할 것):
KUFIM 적용 시 제약:
```

### 1.4 특히 집중할 질문

1. **전화번호 없이도 서비스가 성립하는가?**
   TBD-02가 여기 달려 있다. 비회원 경로가 있는 서비스가 하나라도 있으면, 그 방식이 우리 1안의 근거가 된다.
2. **예상 대기시간이 틀렸을 때 사용자는 어떻게 반응하는가?**
   우리 산출식(F-WAI-07)은 최근 호출 간격 이동 평균이라 초반에 크게 흔들린다. 타 서비스가 이 구간을 어떻게 처리하는지 본다.
3. **화면을 닫아도 호출을 놓치지 않는가?**
   SMS를 제외하기로 한 우리 결정(TBD-03)의 위험을 정량화할 유일한 방법이다.

## 2. 타 대학 축제 서비스 조사

| 축 | 확인할 것 |
|---|---|
| 제공 형태 | 웹 / 앱 / 인스타 링크트리 |
| 기능 범위 | 타임테이블·부스 지도·웨이팅·굿즈 중 무엇까지 |
| 지도 방식 | 실지도 API 위 오버레이인가, 자체 도면인가 |
| 혼잡도 | 제공하는가. 제공한다면 누가 어떻게 입력하는가 |
| 다국어 | 영어 지원 여부 |
| 운영 주체 | 학생회 자체 개발인가, 외주인가 |
| 지속성 | 매년 재사용되는가, 1회성인가 |

> **지도 방식과 혼잡도 입력 주체가 가장 중요하다.** 우리는 도면 기반 + 운영자 수동 입력을 택했는데(MAP-001, STG-002), 다른 학교가 이미 다른 방식으로 실패했거나 성공했다면 그 근거를 확보해야 한다.

## 3. 총학생회 인터뷰

### 3.1 개요

| 항목 | 내용 |
|---|---|
| 대상 | 축제 기획·운영 담당자 (가능하면 2025 일감호축전 경험자) |
| 소요 | 60~90분 |
| 준비물 | 2025년 축제 배치도, 부스 목록(있다면) |
| 목표 | ① Pain Point 도출 ② TBD-01~04 결정 근거 확보 ③ 데이터 확보 일정 합의 |

### 3.2 질문지

#### A. 2025년 축제 실제 상황

1. 메인무대 입장 대기가 가장 심했던 시간대와 대기 길이는 어느 정도였나요?
2. 대기 인원은 어떻게 파악하셨나요? 세는 사람이 따로 있었나요?
3. 그 정보를 누구에게, 어떤 방식으로 전달하셨나요? (무전기·단톡방·구두)
4. 인원 파악이 늦어서 판단이 늦어진 사례가 있었나요?
5. 부스 줄서기는 어떻게 관리되었나요? 부스마다 달랐나요?
6. 학우들이 가장 많이 물어본 질문 세 가지는 무엇이었나요?
7. 운영진이 가장 많은 시간을 쓴 일은 무엇이었나요?

#### B. 운영 구조

8. 부스는 총 몇 개였고, 종류별로 어떻게 나뉘나요?
9. 부스 하나당 운영 인원은 몇 명인가요? 교대가 있나요?
10. 부스 운영자는 스마트폰/태블릿을 쓸 여유가 있나요? 손이 자유로운가요?
11. 축제 당일 부스 배치가 사전 계획과 달라지는 일이 얼마나 잦나요?
12. 타임테이블이 당일 변경되는 일이 있나요? 있다면 어떻게 공지하나요?
13. 상황실은 어디에 있고, 몇 명이 상주하나요?

#### C. KUFIM 기능 검증 — **핵심 구간**

14. **혼잡도를 운영자가 직접 입력해야 한다면**, 몇 분 간격이면 감당 가능한가요? 누가 입력하게 될까요?
15. 혼잡도 4단계(원활/보통/혼잡/매우 혼잡)로 충분한가요? 현장 감각과 맞나요?
16. **웨이팅 호출을 문자로 보내지 않고 화면 표시만 한다면** 어떤 문제가 생길 것 같나요?
17. 학우가 호출을 놓쳤을 때 현장에서 어떻게 처리하는 게 현실적인가요?
18. **전화번호를 받지 않아도** 현장 운영이 가능할까요? 이름 대신 번호로 부르는 방식은 어떤가요?
19. 부스 QR 코드를 부착·관리하는 게 가능한가요? 누가 담당하게 될까요?
20. 관리자 계정을 부스별로 나눠 드리면 교육이 가능한 규모인가요?

#### D. 데이터·협조

21. 부스 목록·타임테이블은 언제쯤 확정되나요?
22. 축제 배치도를 이미지 파일로 받을 수 있을까요? 어떤 형식인가요?
23. QR 코드 인쇄·배포를 총학생회 쪽에서 진행해 주실 수 있나요?
24. 서비스 홍보를 SNS로 도와주실 수 있나요? 언제쯤 공지가 나가나요?
25. 축제 종료 후 이용 데이터를 분석해 공유드리면 도움이 될까요?

#### E. 마무리

26. 저희가 만들려는 것 중에 **현장에서 안 쓰일 것 같은 기능**이 있나요?
27. 저희가 놓치고 있는 게 있다면 무엇일까요?

### 3.3 인터뷰 후 즉시 정리할 것

| 산출 | 반영처 |
|---|---|
| Pain Point 목록 (우선순위 포함) | 요구사항 명세서 재검토 |
| Q14~15 답변 | STG-002 혼잡도 입력 주기·단계 확정 |
| Q16~18 답변 | **TBD-01·02·03 결정** |
| Q21~22 답변 | 데이터 확보 일정 → 4주차 시드 데이터 계획 |
| Q26 답변 | 기능 범위 재조정 (더 줄일 여지가 있는지) |

> **Q16~18은 이 인터뷰의 존재 이유다.** SMS를 빼기로 한 결정이 현장에서 감당 가능한지, 전화번호를 안 받아도 되는지는 운영 경험자만 답할 수 있다.
> 이 답변 없이 6주차 웨이팅 구현에 들어가면 나중에 스키마와 화면을 동시에 갈아야 한다.
