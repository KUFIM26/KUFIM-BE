1. 프로젝트 주차 목표
타 서비스 벤치마킹 분석 및 프로젝트 요구사항 정리
국내 웨이팅 서비스(테이블링·캐치테이블 등) 및 타 대학 축제 웹 서비스 비교 분석
건국대학교 총학생회 인터뷰를 통한 축제 운영 Pain Point 도출
요구사항 명세서 작성 및 1·2단계 기능 범위 확정
미결정 항목(이용자 인증 방식, 전화번호 수집 여부, 호출 알림 수단) 결정
설계 문서 자동 검증 체계 구축

2. 프로젝트 주차 진행 내용
벤치마킹을 인상 비교로 끝내지 않기 위해 비교 축 11개(진입 방식·본인 식별·입력 항목 수·대기 정보 표시·예상 시간 산출·호출 알림·노쇼 처리·취소 흐름·이탈 후 복귀·오류 처리·운영자 화면)와 공통 기록 양식을 먼저 설계하고, 각 축이 어떤 요구사항 결정에 연결되는지 매핑했습니다.
총학생회 인터뷰도 같은 방식으로 27개 문항의 질문지를 작성했습니다. 특히 "전화번호를 받지 않아도 현장 운영이 가능한가", "호출을 화면 표시만으로 안내하면 어떤 문제가 생기는가"를 핵심 질문으로 배치했습니다. 운영 경험자만 답할 수 있는 항목이기 때문입니다.
이를 바탕으로 요구사항 명세서를 작성했습니다. 백엔드 투입 시간이 주 10시간으로 제한되는 점을 고려해, 계획서의 기능 중 신고 제도·스탬프 투어·굿즈 구매·티켓팅·분실물을 2단계로 보류하고 1단계 범위를 축소 확정했습니다.

3. 프로젝트 주차 진행 결과
요구사항 명세서를 완성했습니다. 유스케이스 27건, 기능 요구사항 81건, 비기능 요구사항 32건으로 구성됩니다.
벤치마킹 비교 축 11개와 기록 양식, 총학생회 인터뷰 질문지 27문항을 확정했습니다.
1단계 기능 범위를 스마트 웨이팅(QR)·메인무대 혼잡도 관제·축제 지도·관리자 대시보드로 확정했습니다.
미결정 항목 3건을 결정했습니다: 비회원 익명 토큰 인증, 전화번호 선택 수집, 입장 호출 문자 발송 구현(일일 한도 통제)입니다.
김도현: 벤치마킹 분석 및 인터뷰 설계 주도, 요구사항 명세서 작성, 기능 범위 확정
정근녕: 타 대학 축제 서비스 백엔드 기술 스택 조사, 요구사항 명세서 백엔드 파트 검토, 인증·데이터 관련 미결정 항목 검토

4. 기타(문제점, 해결방법, 자기평가 등)
요구사항을 문장으로만 적으면 문서 간 불일치를 사람 눈으로 잡을 수 없다는 문제가 있었습니다. 실제 점검에서 요구사항 항목 간 ID 불일치·개수 오기 등 결함 11건이 발견되었습니다. 이를 해결하기 위해 문서 정합성·ID 누락·개수 불일치를 자동 대조하는 검증 스크립트를 작성해 문서 수정 시마다 실행하도록 했고, 현재 전 항목 통과 상태입니다.
또한 근거가 약한 제안값 77건을 별도 목록으로 분리해, 인터뷰와 현장 실측 이후 코드 수정 없이 교체할 수 있도록 설계했습니다.
벤치마킹 기록 양식과 인터뷰 질문지로 수집한 내용은 2주차 ERD 확정에 그대로 반영할 예정입니다.
자기평가로는 "무엇을 만들지"보다 "무엇을 만들지 않을지"를 정하는 데 시간을 더 쓴 것이 적절했다고 판단합니다. 다만 부스 목록·타임테이블·캠퍼스 도면 등 실데이터 확보 일정이 미정이므로, 2주차에 이를 우선 처리할 계획입니다.
