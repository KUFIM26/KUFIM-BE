서비스 기능 구조 및 데이터 구조 확정
1주차 요구사항 기반 전체 기능 정의서 작성 및 기능별 우선순위 설정
ERD 설계 및 웨이팅·지도 등 핵심 기능 간 데이터 연관 관계 정립
프론트엔드·백엔드 간 통신 구조를 정의하는 API 구조 초안 작성
전체 시스템 아키텍처 다이어그램 완성
산출물 간 정합성 자동 검증

2. 프로젝트 주차 진행 내용
1주차 요구사항을 구현 단위로 분해했습니다. 기능을 화면·기능·상태 세 축으로 나누고 각 기능에 우선순위(필수·권장·선택)와 담당자를 지정했습니다. 특히 웨이팅은 대기·호출·입장·취소·노쇼 다섯 상태의 전이 조건과 전이 주체를 명시해, 상태를 누가 바꾸는지를 문서 단계에서 확정했습니다.
데이터 구조는 MySQL과 Redis의 역할을 분리하는 원칙으로 설계했습니다. 대기열 순번 계산은 Redis가 담당하고 모든 상태 전이는 MySQL에 이력으로 남겨, Redis 장애 시 MySQL의 활성 웨이팅으로 대기열을 재구성할 수 있도록 했습니다. 중복 등록 차단은 MySQL이 부분 유니크 인덱스를 지원하지 않아 DB 제약으로 만들 수 없었고, Redis SETNX와 트랜잭션 내 재확인 방식으로 해결했습니다.
API는 명세 문서를 원본으로 두고 타입 정의를 자동 생성하는 구조로 구성했습니다.

3. 프로젝트 주차 진행 결과
기능 정의서를 완성했습니다. 요구사항을 이용자·관리자 화면과 기능 단위로 분해하고 우선순위·담당자·주차별 개발 순서를 배정했습니다.
ERD를 확정했습니다. 웨이팅·혼잡도·지도 도메인의 엔티티 관계와 상태 이력 구조를 정의하고, 영구 데이터와 실시간 데이터의 경계를 스키마 수준에서 나눴습니다. 초기 스키마와 더미 데이터를 실제 적재해 참조 무결성과 업무 규칙 위반이 없음을 확인했습니다.
API 구조 초안을 작성했습니다. 자원 단위 REST 엔드포인트와 실시간 갱신용 WebSocket 토픽, 공통 에러 코드 체계를 정의해 양측이 같은 계약 위에서 병렬 개발할 수 있게 했습니다.
아키텍처 다이어그램은 배포 구성, 논리 계층, 핵심 시퀀스, 장애 대응 경로로 구성했습니다.
김도현: 기능 정의서 작성 및 우선순위 설정, 프론트엔드 관점 API 구조 초안 작성, 시스템 아키텍처 다이어그램 작성
정근녕: ERD 설계 및 데이터 모델링, 테이블·인덱스 구조 정의, 백엔드 API 구조 초안 검토

4. 기타(문제점, 해결방법, 자기평가 등)
산출물이 늘면서 요구사항·기능·API·스키마가 서로 어긋나는 문제가 생겼습니다. 사람이 눈으로 대조할 규모가 아니라고 판단해, 문서 간 ID 참조·개수 주장·컬럼 일치·enum 값을 자동 대조하는 검증 스크립트를 작성했습니다. 이번 주차 산출물에 실행해 기능 정의서에서 참조되지 않은 요구사항, 스키마에만 존재하고 문서에 누락된 컬럼 등 불일치를 발견·수정했고 현재 전 항목 통과 상태입니다. 문서를 고칠 때마다 다시 실행하므로, 설계 변경이 다른 문서에 반영되지 않는 상황을 구조적으로 막을 수 있습니다.
이 과정에서 1주차 요구사항이 기능 정의서에 누락 없이 반영되었음을 확인했고, 확정된 요구사항 명세서를 함께 제출합니다.
계획서의 "신고 기능 데이터 연관 관계"는 1주차에 2단계로 보류 확정한 범위이므로 제외했습니다.
자기평가로는 구현 전에 상태 전이와 장애 복구 경로를 문서로 확정한 것이 6주차 웨이팅 구현의 위험을 줄였다고 판단합니다.
