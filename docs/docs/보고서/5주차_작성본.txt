진행내용
4주차에 구축한 개발 환경 위에서 3주차에 확정한 Figma 프로토타입을 실제 동작하는 화면으로 구현했습니다. 프로토타입에서는 화면 구성을 눈으로 확인하는 데 그쳤으나, 이제 운영진이 등록한 내용이 이용자 화면에 그대로 반영됩니다. 시안을 React 페이지로 옮기면서 3주차에 정리한 디자인 토큰을 그대로 참조하도록 해 시안과 구현이 어긋나지 않도록 했습니다.
이번 주차는 백엔드 연동보다 화면 흐름을 먼저 완성하는 순서를 택했습니다. API 응답 구조를 먼저 정하고 화면을 맞추면 화면이 실제로 필요로 하는 데이터가 뒤늦게 드러나 수정 비용이 커지기 때문입니다. 화면으로 필요한 데이터를 먼저 드러낸 뒤 그 결과를 바탕으로 API 명세를 작성했습니다.
라우팅은 이용자와 관리자 경로를 분리했고, 날짜·무대·카테고리처럼 내용만 거르는 조건은 검색 조건으로 두어 특정 화면을 링크로 공유할 수 있게 했습니다. 화면 수가 많아 수동 확인만으로는 변경에 따른 오류를 놓치기 쉬워 자동 검증 절차도 함께 마련했습니다.
진행결과
이용자 화면을 구현했습니다. 홈, 전체 메뉴, 축제 지도, 부스·시설 목록과 상세, 공연 일정과 상세, 공지와 알림함, 내 대기표, QR 안내와 접수로 구성됩니다.
관리자 화면을 구현했습니다. 공지·공연·부스의 등록과 수정, 시설 지도 위치 지정, 부스별 대기 명단과 호출·취소, 운영 상태와 예상 대기시간 설정을 포함합니다.
QR 안내에서 접수 폼을 거쳐 대기표를 발급받고 취소까지 이어지는 흐름을 완성했으며, 입력값 검증을 함께 적용했습니다.
모바일 기준 반응형 레이아웃을 적용하고 화면 접속과 접수·취소 흐름을 테스트로 검증했습니다. 프론트엔드를 배포해 백엔드 연결 전에도 실제 모바일 기기에서 화면 흐름을 확인할 수 있게 했습니다.
김도현: 이용자·관리자 전체 화면 구현, 디자인 토큰 적용, 라우팅 구조 설계, 반응형 적용, 화면 검증 테스트 작성 및 배포
정근녕: 공연·부스·공지 조회 API를 대상으로 Swagger 명세 1차 작성, 응답 구조와 화면 설계의 정합성 검토
기타
(문제점, 해결방법,
자기평가 등)
계획서의 메인무대 혼잡도 관제와 WebSocket 실시간 반영은 완료하지 못했습니다. 화면과 데이터 구조 설계까지만 진행했고 실시간 연동은 6주차로 넘겼습니다. 백엔드 API가 연결되지 않은 상태에서 실시간 통신을 먼저 붙이면 값이 틀렸을 때 화면과 서버 중 어느 쪽 문제인지 가리기 어렵다고 판단했습니다.
화면을 실제로 만들면서 시안과 기능 정의서의 불일치가 드러났습니다. 상세 화면이 없는 항목과 행사 기간이 맞지 않는 부분은 임의로 채우지 않고 기록해 총학생회 확인 후 반영하기로 했습니다.
현재 데이터는 예시 데이터이며 관리자 경로는 인증이 없는 상태입니다. 4주차 멘토링에서 제시된 권한 관리 의견을 반영해, 백엔드 연결 시 로그인과 서버 측 권한 검사를 함께 적용하겠습니다.
화면을 먼저 완성한 선택은 적절했다고 판단합니다. 다만 연동이 뒤로 밀린 만큼 6주차에는 API 구현과 화면 연결을 함께 진행하겠습니다.
